# Terrane

Terrane turns one directory into a world you travel through. Folders are
plateaus, files are blocks standing on them, and going deeper into the
hierarchy means going down in scale. From inside that world you can open,
rename, move, copy and remove real files, with undo.

It is two parts: a small local service that is given exactly one directory,
and a browser interface that talks only to that service.

## Try it

Open <https://dnoice.github.io/terrane/> and Terrane starts on its demo
world: a made-up studio drive of about twelve thousand files in code
projects, photos, film footage, music, design work, documents, an old
laptop's archive and downloads, built in the page from one seed. Every
feature works on it, changes and undo included, and nothing leaves the
page; a reload starts the world again.

The same page runs locally with nothing but Node.js:

```bash
npm run demo
```

It prints an address to open. To try the real service, and every
operation on real files, somewhere that does not matter, write the same
world to disk and point Terrane at it:

```bash
npm run demo -- write C:\temp\terrane-demo
npm start -- C:\temp\terrane-demo
```

## Launch

Requires Node.js 22.5 or newer. Nothing to install.

```bash
node server/terrane.mjs "C:\Users\DnnsS\OneDrive\Desktop\dd1\projects"
```

The service prints its address (`http://127.0.0.1:4173/`) and opens it in
the default browser. Stop it with Ctrl+C. The directory can be a whole
drive, such as `D:\`.

Open the page only at that address to see your own directory. Opened
from another server or from GitHub Pages, the page has no service behind
it and runs the demo world instead; opened from disk, it says how to
start Terrane and links to this repository.

The page opens on a loading sheet: the T is surveyed and laid down
stratum by stratum while the service connects and the first survey
arrives, and the line beneath the TERRANE wordmark says which of those
is happening. When the first batch is drawn the sheet is excavated
away. Once the page is ready, a click or any key skips what is left of
the intro. With reduced motion the sheet shows the finished T and leaves
without moving.

From the second launch on, the page starts warm. The service keeps the
last complete survey of the directory (names, sizes, dates and flags,
never what a file holds) in the dataset home, the folder described under
Developing against real data, and the page draws that tree at once,
with a notice that it shows the directory as the last
session surveyed it. The service then checks that tree against the
disk by folder modification times: it reads again only the folders
whose time changed, each new folder whole, and a folder that is gone
through its parent. Until the check is in, changes wait and say so,
while opening, revealing, copying and a terminal do not; then the world
takes on what changed, keeping the folder you are in, the selection and
the eye, and a notice says how many folders were read again and how
many files changed, are here now and are gone, or that nothing changed
since the last session. A file rewritten in place leaves its folder's
time as it was, so a sweep follows that reads every other file's size
and time, a few at a time, and the world takes on what it finds as it
takes on any outside change. A kept tree that cannot be read whole is
set aside, and the page surveys afresh and says so; a check that fails
keeps the last session's tree, says why and offers Survey again.

| Option | Effect |
| ------ | ------ |
| `--read-only` | Refuses every action that changes the disk. Start here on anything you care about. The warm start's tree is still kept in the dataset home, outside the directory. |
| `--port <n>` | Preferred port. The next free one is used if it is taken, or on Windows refused because another program holds it. |
| `--no-open` | Does not open the browser. |
| `--no-watch` | Does not watch for outside changes; use Refresh. |
| `--no-warm` | Keeps no tree of the last survey and serves none: every launch surveys before it draws, and the service writes nothing to the dataset home. |
| `--flavor <id>` | Every page that opens the service starts in that flavor once, as if chosen in the guide: `blender`, `autocad`, `sketchup`, `maya`, `3dsmax`, `rhino`, `solidworks`, `unity`, `unreal`, `earth` or `terrane`. A flavor chosen in the guide afterwards holds until a launch names a different one. |
| `--region-threshold <n>` | Above n entries (folders and files) the service keeps the tree and the page draws it in regions; 100,000 unless `TERRANE_REGION_THRESHOLD` says otherwise, and 0 for every tree. See Very large directories. |

```bash
node server/terrane.mjs "E:\digiSpace" --read-only
npm start -- ~/Music --port 5050
```

## Very large directories

Up to 100,000 entries, folders and files together, the page holds the
whole tree, as it always has. Above that the service keeps the tree and
the page holds only the parts near you: the folders standing open in
view, and those the eye is about to reach. A drive of millions of files
is travelled as a small one is: with 5,000,000 entries the page's
script heap peaked at 41.7 MB and no task ran more than
12.1 ms of script (What was verified has the figures at every
size).

The page decides at the start. A snapshot or the warm cache says how
many entries there are, and a tree above the threshold is drawn in
regions from the first frame. A directory Terrane has not surveyed before is surveyed as usual
until it passes the threshold; then the survey stops, the loading sheet
says "Large directory: reading it in regions", and the service reads the
directory itself. That reading becomes the warm cache, so the next
launch draws at once and the service checks the tree in place by folder
modification times while changes wait.

What is the same as with a whole tree: travel, the lenses, Contents and
the inspector for every folder you reach, the time view, strata,
landmarks, the remembered view and the address, Quick look, and every
operation on files. Each folder arrives with its figures (size, files,
folders, kinds, bytes by last change and typical age), so a closed mass
is drawn, coloured and lowered from them before anything inside it has
been read.

What is asked of the service, and arrives in a moment rather than at
once:

- A folder's contents, as you approach it or go there. Going to a
  folder, selecting it or revealing a file waits for its folder first.
  The status line ends "Regions · N of M entries held".
- Find. The service searches the whole tree and counts every match.
  Findings lists them 5,000 to a page in the order chosen, with
  Previous and Next on its count row to turn through the rest, and the
  world pins the matches it holds.
- The Survey, Verify by content, Working sessions, Changed with it and
  the traverse, the palette's folders and files, the quick searches'
  counts, and Cleanup's suggestions for a folder, counted across every
  level beneath it.
- The Shelf's items, found by path across the tree before it acts on
  them ("Finding the shelf's 14 items across the tree…"). Until then a
  row whose folder is not loaded shows the size it had when it was put
  on the shelf, and its tooltip says so.
- Compare's two folders, each read as its region before they are
  compared ("Reading both folders…"), and its Same name elsewhere,
  which asks the service for folders of that name across the tree.

What is cut to a size, and says so:

- Select all in Findings takes the first 1,000 matches. Add all to the
  shelf stops where the Shelf is full, at 1,000 items, and says how
  many of the matches it put on.
- Cleanup lists the 1,000 largest of each group and says so; the rest
  come up after a move. Its duplicates come from the 400 largest sets
  the survey found.
- Compare matches the entries each folder's region holds, its 5,000
  largest, while its figures, kinds and ages are the whole folder's.
  Where a folder holds more, a note says how many of its smallest were
  not compared and that an entry listed as only in the other folder may
  be among them. Select all on one of its groups takes the 1,000
  largest items (5,000 with a whole tree) and says how many of how
  many.
- The Survey's empty folders, sealed folders and links show their first
  300 rows, as with a whole tree, and say "The first 300 of N.". Export
  CSV saves the first 1,000 of a Survey list and the page Findings
  shows, and each notice says which.
- A folder of more than 5,000 entries holds its 5,000 largest; the rest
  lie in its scree, and Contents says how to find them with `in:`.

What is not available at that size: the twins of an open archive. I
still opens an archive, and its notice says twins are not looked for.

Changes made outside Terrane reach the service's tree whether or not a
page is open, so a page opened later shows them. Where the disk is not
watched (`--no-watch`, or on Linux above 15,000 folders), the service
checks its tree by folder times when a page connects. Regions the page
no longer needs are let go once it holds 200,000 entries, down to
150,000, but never the folder you are in, the selection, a benchmark,
the return point or anything standing open in view.

The service holds the tree in about 730 MB at 5,000,000 entries; for a
tree that size, start it as
`node --max-old-space-size=4096 server/terrane.mjs <directory>`, as the
measurements did. A threshold above 100,000 keeps a larger tree whole in
the page, at the cost of memory and frames: a whole tree of 400,000
entries ran a task of 60 ms.

## Developing against real data

Development runs against a recorded copy of a real directory, so nothing
real can be changed by a bug, a test or a half-built feature.

```bash
npm run dev -- --target "C:\Users\DnnsS\OneDrive\Desktop\dd1\projects"
npm run dev
```

The first form remembers the target; after that `npm run dev` is enough.
`npm run dev -- --flavor blender` is remembered the same way, so every
later run opens in Blender's flavor.
It does four things:

1. Takes a structure snapshot if the newest is more than six hours old:
   every folder and file with its name, size, dates and type, never its
   contents. About 230,000 entries take under three seconds.
2. Starts Terrane with `--snapshot`. In this mode the service reads only
   the snapshot; every change, open, reveal, content preview and archive
   listing is refused with a sentence saying why.
3. Updates the thumbnail dataset in the background at below-normal
   priority. Only new or changed images are read.
4. Takes a new snapshot every hour while it runs. The open page offers to
   rescan when one lands.

| Command | Does |
| ------- | ---- |
| `npm run snapshot -- <dir>` | One snapshot now |
| `npm run export` | The newest snapshot as a CSV table and a JSON tree, in an `exports` folder beside it; name a dataset folder or a `.db` file when there is more than one |
| `npm run demo` | Serve the repository as GitHub Pages does, so the page runs the demo world |
| `npm run demo -- write <folder>` | Write the demo world to disk: text files with their contents, large files sparse at their sizes |
| `npm run thumbs` | Update thumbnails; `--stats` shows what is stored |
| `npm run thumbs -- --huge` | Also thumbnail images over 80 megapixels, one at a time |
| `npm run thumbs -- --heavy-svg` | Also render SVGs over 512 KB through Inkscape |

Datasets live in `%LOCALAPPDATA%\terrane\datasets\<name>` (on other
systems `~/.cache/terrane/datasets`), outside the project and outside
OneDrive; `TERRANE_DATA` names another place for them. They hold real
file names, so they stay local. Both are SQLite files and can be
queried directly, for example
`SELECT folder, name, size FROM entries ORDER BY size DESC LIMIT 20`.
`npm run export` writes a snapshot out for anything else: one CSV row
per folder and file (kind, path, size, files and folders beneath,
modified time in UTC, flags), and the same entries as a nested JSON
tree.
The warm start's cache sits in the same folder for its directory, as
`warm-<hash>.ndjson.gz` and its meta `warm-<hash>.json`, and holds the
same kind of data as a snapshot. Snapshot mode keeps none.

The checks never write to the real dataset home and never launch a
program. Every service `npm test` and `npm run ui-check` start keeps its
data in a `TERRANE_DATA` folder of its own, and where a check asks for
Open, Reveal or a terminal, the launch is written to a
`TERRANE_LAUNCH_LOG` file as one line instead of being started.

### Synthetic snapshots and the scale harness

Very large trees are measured on directories that do not exist.
`tools/make-synthetic.mjs` writes a structure snapshot of a made-up tree
of 1,000 to 10,000,000 entries from one seed, without creating a file:
code projects with `.git` and `node_modules`, photos, video, music,
documents, data and archives, up to twelve levels deep, with working
sessions, bulk writes, files of the same size, hidden names, links and
folders that could not be read. The service serves it in snapshot mode
as it serves a snapshot of a real directory. It refuses to write into
the `projects` dataset or over a snapshot of a real directory, and a
snapshot it writes into the dataset home (`synthetic-<size>`, unless
`--out` names a folder) stays there until it is deleted.

```bash
node tools/make-synthetic.mjs --entries 1m --out C:\temp\synthetic-1m
node server/terrane.mjs --snapshot C:\temp\synthetic-1m
```

`tools/scale.mjs` measures Terrane at several sizes, one heavy process
at a time. It generates each point in the OS temp folder, drives the
page over it through the `scale` scenario of the interface check (the
overview, eight levels down from the keyboard, two searches and a
reveal, the Survey and a reveal from it, then, in regions, half the
budget of held entries and a walk down again), traces the page, and
prints a table: the first box drawn cold and after a reload, the page's
script heap settled, at its peak, after the tour and after a
collection, the longest task's script and what ran in it, the regions
held, and the service's search and survey times. `--service-only`
measures the service alone. Before a point of a million entries or more
it waits for 6 GB of free memory, before every browser for no other
headless browser, and it gives each process an explicit heap. It deletes
each dataset after measuring it and writes the figures as JSON to
`terrane-scale` in the OS temp folder.

```bash
node tools/scale.mjs
node tools/scale.mjs --points 5m --nogl
node tools/scale.mjs --points 1m,2m,5m --service-only
```

Names are printed on the blocks themselves, lit and shadowed with them:

The even channels changed how every folder's rows fall, so each

**Time.** The world looks back to one of 19 dates on a fixed ladder, from
a day to 30 years back. Whatever changed after it lies flat, crossed
corner to corner, and a closed mass is lowered to the share of its bytes
it kept unchanged. Footprints and positions stay as they are now, so a
place can be compared with itself. The As of stepper in the title block
shows the date and is reachable by Tab; the inspector's Since section
sums what changed and what did not, and lists where the change is.
Escape returns to the present.

**Landmarks.** A benchmark measures a folder at a moment: its size, files,
folders and its 64 largest direct entries. The Places tab lists every benchmark
with what changed since (entries gone, here now, grown and shrunk), with
Fly there, Measure again, Forget and Forget all, and holds the return
point. `is:benchmark` in Find finds them. Terrane's own renames and moves,
and their undo, carry benchmarks along; a folder renamed or removed from
outside is marked missing, with Forget, and never silently dropped.
Places are kept in this browser for this directory at this address: another
browser, profile or port keeps its own, and benchmarks of a snapshot are
kept apart from those of the live directory. To carry them across,
Export places (in the Places tab or the palette) saves the benchmarks,
the return point and the saved searches as
`terrane-places-<directory>-YYYY-MM-DD.json`, and Import places… takes
the file in elsewhere. A benchmark already there is updated only when
the file's measurement is newer, at most 64 are kept, and the notice's
Undo puts everything back. A file for another directory, or for a
snapshot when the live directory is open (or the reverse), is refused
and nothing changes.

**Working sessions.** Files whose last changes follow each other within 30
minutes make a session; folders whose names start with a dot are left
out. The Survey tab's Working sessions section lists the newest 40, and a
session written at once (an extraction, a copy or an install) is labelled
so. Enter on a row puts `session:N` in Find: Findings lists its files in
the order they changed, and the world draws the traverse through them.
ArrowDown and Enter in Findings step from stop to stop. A selected
file's inspector says what changed with it: its session, the eight files
nearest to it in time with their times, and Show all as `session:N`; the
context menu's "Show its working session" and the palette do the same,
and a file in no session says why.

**Strata.** The inspector's Bytes by last change, for the folder you are
in or a selected folder, splits its bytes into six strata (under a day, a
week, a month, a year, three years, older) with a sentence such as "81% of
these bytes have not changed in over a year". The Age lens colours a
closed mass by the same table, and Contents sorts by it too: Untouched
lists the longest untouched first, a folder by its typical age and a
file by its last change.

**Archive interiors.** I on a zip archive (or a jar, war, ear, apk, aab,
whl, xpi, nupkg, vsix or ipa) reads its directory through the service
without unpacking it and walls what it lists in on the archive's own
footprint. In the ledger I acts on the row the cursor is on; elsewhere,
on the selection. Contents lists the archive like a folder, the
breadcrumbs go through it, and a path inside reads `x.zip!/inner/file`.
Nothing inside can be changed, opened or revealed. The interior closes
when the archive changes on disk, and is unavailable in snapshot mode.
Other formats are named and refused, and search does not reach inside.

**Quick look.** P, the inspector's Quick look, Preview's or the palette
shows the selected file in a large sheet before anything is opened: its
text, the first 256 KB with line numbers; its picture, as the 480 px
thumbnail, or the file itself only when it is 2 MB or less and not an
SVG; its sound or film, in the browser's own player, which reads it in
byte ranges and never plays by itself. A link, an archive entry and any other kind get
their facts and a sentence, and so does everything but a picture's
thumbnail in snapshot mode. ← and → step to the previous and next file
of the list shown, Contents or Findings, Home and End to the first and
last; a long line or a long text scrolls to its edge first, and a
player keeps its own keys.

**Preview.** The right panel's second tab is a quick look docked
beside the world. It follows the selection, so a folder or a search can
be read through item by item, from the ledger or the world, without
opening anything or covering the view. Choose PREVIEW on the right
panel's strip, or Ctrl+K, "preview", Enter, which opens the right panel too when `]` or a narrow
window hid it and puts focus in the tab. The Inspector stays the
default, and the tab chosen is kept in this browser. Preview's head
says at once what the item is, the folder it is in (a button back up
to it) and its facts; its body follows once the arrows rest, so holding
an arrow through a list reads only where you stop, and a read a newer
selection overtakes is stopped. It shows:

- a text's first 256 KB with its lines numbered, what kind of text it
  is, its lines and line endings; Wrap lines, kept in this browser and
  also in the palette, lets long lines run on instead;
- a picture through its thumbnail only, the largest that fits, with its
  size in pixels and its colour; never the file itself;
- sound and film in the browser's own player, read in byte ranges,
  never playing by itself, and stopped by the next step;
- a zip archive's listing: what it holds, unpacked and packed, its
  locked and escaping entries and its top level, with Look inside (I);
- a symbolic link's target, never followed, with Select when the
  target lies inside the directory;
- a folder's summary: its bytes by kind, by age, and its ten largest
  entries, each a row that selects it;
- several selected: what they are, largest first, and what they weigh.
  Enter on a row (or on the pane, the first) reads one while the
  selection stays whole, ← → step through them, and Esc goes back to
  the list.

Where there is nothing to show, Preview says why in one sentence beside
the facts: a sealed folder, an empty folder or file, snapshot mode (no
contents are read there, though a picture's thumbnail still shows), an
entry of an open archive, a kind it does not read, an item removed from
outside since, or a read that failed, with Try again. In a very large
directory a folder's largest entries arrive once its region does; the
demo world plays one tone for every sound and one film for every video,
and says so. In the pane, ← and → step to the previous and next item of
the list the ledger shows, or of the item's folder, Home and End to the
first and last, and a long text scrolls to its edge first; ↓ and ↑
reach the rows; Enter opens a file or goes into a folder; P, or the
Quick look button, opens Quick look where its sheet shows more (a
text, a picture, a player), with focus back in Preview when it closes,
and elsewhere says why it would not. While Preview is not on screen,
or a sheet covers the page, it reads and plays nothing.

**Compare.** The right panel's third tab sets two folders side by
side: two copies of a project, a photo folder and its backup, a folder
now and at its benchmark. It shows what each weighs and holds, their
makeup by kind and by last change on one scale, and what differs, each
list ranked by size. It only reads: nothing it does changes the disk.
To start it:

- Select a folder and press C (on a file, its folder; with nothing
  selected, the folder you are in), then click the other folder in the
  world, press Enter on it in the ledger, or travel to it and choose
  Compare with where I am on the banner. Escape, or the banner's
  Cancel, ends the choice and brings back any earlier comparison. A
  file clicked stands for its folder, and the sentence says so; a
  folder that cannot be compared is refused in words and the choice
  goes on.
- Right-click a folder and choose Compare with… (on a file, Compare
  its folder with…; on the ground, Compare this folder with…). While
  you choose, the menu of any other folder offers Compare with "<the
  first folder>".
- With two folders selected, press C or choose Compare these two on
  the menu, and they are compared at once; opening the tab does the
  same while nothing is being compared, and otherwise its head offers
  Compare the 2 selected instead. Drag one or two folder rows from the
  ledger onto the Compare tab: two are compared, one starts the
  choice.
- On a folder with a benchmark, Compare with its benchmark on the menu,
  Compare with now in the inspector's Benchmark section, or Compare on
  its row in the Places tab.
- Choose COMPARE on the right panel's strip, or Ctrl+K, "compare":
  Show Compare first, then Compare with…, Compare the two selected
  folders, Compare with its benchmark, Swap the compared folders and
  Clear the compared folders.

Empty, the tab says what it is for and offers Compare "<folder>"
with… for the selected folder, or the one you are in, and where they
apply Compare the 2 selected folders and Compare with its benchmark;
under them, Same name elsewhere lists up to six folders of that name
across the tree, largest first, and a press on one compares it. The
offer follows the selection. While you choose, the tab says how, with
Cancel.

The head names the pair ("Two folders named node_modules", "Coast and
Pictures/Coast", "harbor-api, now and then") over its two sides, each
behind its mark, ● for the first and ○ for the second, with its name,
the folder it is in and its size; a side pressed is selected and
framed. Two folders of one name are told apart by the shortest ends of
their paths that differ. Swap and Clear stand under the sides; Clear's
notice has Undo. A sentence then says what was found, as in "The second
is 291 MB smaller, with 53 fewer files. Of 77 names, 24 are in both and
the same, 53 only in 2020/2020-04 Night sky and none only in
Pictures/2020-04 Night sky.", and the tab shows:

- the figures side by side: size, files, folders, entries, the newest
  change, and the date since which half of the bytes have not changed;
- By kind and By last change, each two bars on one scale, so the
  smaller folder's bar is the shorter, with a key of the largest kinds
  and of the six strata;
- What differs, four groups, each with its count and size: Only in ●
  and the first's name, Only in ○ and the second's, In both, changed,
  and In both, the same. The first group with anything in it is open;
  the same is closed until opened.

Entries are matched by name, as the system compares names: on Windows
and macOS `README.md` and `readme.md` are one entry, on Linux two. A
file has changed when its size differs or its last change differs by
more than 2 seconds (FAT keeps time in 2-second steps); a folder when
its size or the number of files or folders in it differs, never by its
own time. An entry that is a folder on one side and a file on the
other, that cannot be read on one, or that is a link on one only, has
changed too. A changed row's line says how, as in "● 10 B · ○ 2.44 KB ·
larger in ○" or "same size; changed later in ● (11/02/2026,
11/01/2026)". No file's contents are read.

A group draws 100 rows, then Show 100 more. Its Select all selects
what it lists, both copies of an entry in both folders, up to 5,000
items, the largest first, and says how many of how many. Each list is
one Tab stop: ↑ and ↓ step through it and Home and End reach its ends;
Enter, or a click, selects the item in both folders and frames the
copy in the first, and Enter again frames the other; → on a folder in
both, marked with a chevron, or a double-click, compares inside it, and
← or Back out one level returns; K puts the item, both copies where it
is in both, on the Shelf, and K again takes it off. The Guide lists
these keys under Looking closer.

Against a benchmark the groups read No longer here, Here now, not then,
Changed since and The same, as the Places tab does. A benchmark kept
its 64 largest entries by name with their sizes and file counts, and

among the 64 largest then.

The pair is kept by path as long as the page, while you travel and

and their Undo. A folder moved or removed outside Terrane is said to be

**Totals and quick searches.** While more than one item is selected,
the Contents and Findings count rows say what the selection weighs, as
in "3 selected · 1.2 GB", counting an item inside another selected
folder once. The Survey tab's Quick searches counts four common
questions, Big and stale (`>100mb older:1y`), Large media
(`kind:video,audio,image >50mb`), Changed this week (`newer:7d`) and
Empty folders (`is:empty is:folder`), and Enter runs one into Findings.
`ext:` and `kind:` take comma lists, as these do.

In the time view, working sessions and strata, "changed" means a file's
last modification time. A copy, a checkout or an extraction restamps the
files it writes, so they read as changed then, never as created or
arrived.

**Duplicate cleanup.** Under a group of duplicate candidates that Verify
by content has confirmed, in the Survey and in the inspector, Keep
newest and Keep oldest (and the inspector's Keep this one) keep one file
and move the other copies to the holding area as one change. Between
copies with the same last change, as copies made by Explorer have, the
path that sorts first is kept, so a refresh never changes which. A
confirmation names what is kept, what moves and the size reclaimed. The
copies are hashed again first, and one that changed since it was
verified stops the whole move. A group compared by sampling, its files
over 16 MB, is called probable and its confirmation says so; a group
not yet verified offers only Verify by content. A verification survives
a refresh for every file whose size and last change are unchanged, and
an Undo that brings a file back from the holding area.

**Cleanup.** The right panel's fourth tab suggests what in one folder
could go, ranked by the space it frees, and moves what you leave
checked to the holding area as one change. Right-click a folder and
choose Suggest cleanup here (on a file, Suggest cleanup in its folder;
on the ground, for this folder), choose CLEANUP on the right panel's
strip, or Ctrl+K, "cleanup": Show Cleanup, or Suggest cleanup for this
folder, whose line names the folder. The folder is the selection if it
is a folder, else the selection's folder, else the folder you are in.
The tab's head names it with its size, files and folders, and two
buttons widen it: "in <parent>" and, deeper down, Whole world. Once you
have chosen a folder the tab keeps it while you select and travel, and
a bar under the head offers Suggest for it when you select or travel
to another. Under the head it says what the move would free, as in
"Could free 4.2 GB · 34% · 63 items", above one button that says what it
moves before it is pressed, "Move 63 items, 4.2 GB". Four groups
follow, the one that frees most first, each with its count and total,
the rule that fills it in words, its rows, and a Move button of its
own:

- **Duplicates**: copies Verify by content found identical, never a
  name or a size alone. Each set keeps one copy, shown first with a
  check and never moved: the newest, or the oldest with Keep oldest,

  set compared by samples, its files over 16 MB, is marked probable on
  its rows, in its note and in the confirmation. Sets that only share a
  size are counted, with Verify by content beside them.
- **Big and stale**: files over 100 MB not changed in a year, the
  thresholds of the Big and stale quick search. A copy a duplicate set
  keeps or suggests is not listed here again.
- **Caches and build output**: folders a tool makes and makes again,

- **Empty folders**: folders that hold nothing at all, hidden files

Read-only and snapshot mode show every suggestion with each Move

cannot be verified. A warm start waits until the last session's tree is
checked. In a very large directory the service counts the folder across

- **Copy paths**: their absolute paths, one per line.

apart from the live directory's, and holds at most 1,000 items; another

**Copy as.** Ctrl+C copies absolute paths. The context menu and the
palette also copy names, and paths relative to the directory, for one
item, a selection or the folder you are in. Relative paths use `/` on
every platform, the directory itself reads `.`, and an archive entry
reads `x.zip!/inner/file`.

**Lists as CSV.** Export CSV on the Contents and Findings count rows
saves the rows listed, in the order shown. The Survey's last section,
Export as CSV, saves its largest files, duplicate candidates (with each
file's group and whether it was confirmed), empty folders, sealed
folders (with the error) and symbolic links, and the palette offers all
seven. The columns are name, path, kind, size_bytes and modified (ISO
8601, UTC), and the file is named
`terrane-<directory>-<list>-YYYY-MM-DD.csv`. It is made in the page, so
it works in every mode. A text cell that begins with `=`, `+`, `-`, `@`,
a tab or a carriage return is written with a leading apostrophe, so a
spreadsheet shows it as text instead of running it as a formula.

**A terminal here.** "Open a terminal here" on a folder, "in its folder"
on a file and "in this folder" for the folder you are in, the
inspector's Terminal here and the palette ask the service to start the
system's terminal with that folder as its working directory: Windows
Terminal (`wt.exe -d .`), else a new `cmd.exe` window, on Windows;
Terminal on macOS; `x-terminal-emulator`, else `gnome-terminal`, on
Linux. A terminal can change anything, so read-only and snapshot mode
show it unavailable with the reason, as do an open archive and a folder
that cannot be read.

### Safety model

- The service reads and writes only inside the directory named on the
  command line. Paths are root-relative; traversal segments are refused,
  and symbolic links that lead outside are refused for both reads and
  writes.
- It never overwrites. A name collision stops the whole batch before
  anything moves, and offers Keep both.
- It never deletes directly. Remove moves items into `.terrane-trash`
  inside the authorized directory, so the move is atomic and reversible.
- The holding area is refused by where it is, not only by its name: in
  any case, by its short name, through a link or a junction that leads
  there. Its index is read as untrusted data, so a record planted in it
  can neither move nor delete anything outside its own slot, and the
  holding area is used only while it is a plain folder.
- A symbolic link is followed only to an end inside the directory, for a
  preview, an archive listing, a hash, Open and Reveal; a copy or move
  never carries a relative link to where it would point outside.
- Every change records its inverse in a journal kept beside the holding
  area, so Undo works after a restart. Journal paths pass through the
  same guard as a request. Undo refuses, with the reason, if the disk has
  changed in a way that would make the undo destroy something.
- A cancelled copy removes only the paths it created, newest first, and
  folders only when empty. Items finished before the cancel stay and can
  be undone.
- A batch rename is checked whole before its first rename: every path
  through the guard, every new name against the system's rules, no path
  twice, no item inside another, no new name that something else has
  now (so chains and swaps are refused), and no two new names alike in
  one folder as the filesystem compares names. One that stops part way
  journals what it finished.
- An Undo that stops part way, because another program holds an item,
  keeps in the journal only what is still to go back, and saves it
  before it says how many items went back, so Undo again resumes, after
  a restart too.
- A terminal starts only in a folder whose real location is inside the
  root and outside the holding area. The folder is its working
  directory, never an argument; the programs and their arguments are a
  fixed list, started with `shell: false`, so no command line is ever
  built from a path. Read-only and snapshot mode refuse it.
- Sound and film are read in byte ranges of at most 8 MiB, after the
  same checks as any preview; snapshot mode refuses every read of a
  file's bytes.
- Preview only reads, and sends nothing that changes the disk: a
  text's first 256 KB, and sound and film in byte ranges, through
  `GET /api/raw`; a zip's listing through `GET /api/inside`; a link's
  target through `GET /api/stat`, read from the link's text and never
  followed; each with the checks of any preview. A picture reaches it
  only through the thumbnail routes, never as the file. In snapshot
  mode it asks for no file's bytes at all.
- Compare has no route of its own and sends nothing that changes the
  disk. It compares names, sizes, counts and times the page already
  holds, never a file's contents; in a very large directory it reads
  each folder through `GET /api/region`, and its Same name elsewhere
  through the `places` question, `GET /api/places`, both behind the
  token and the Host check like every route. Its Select all and K only
  select and gather; what is then done to them goes through the
  operations as anywhere else. It keeps nothing in the browser.
- Cleanup deletes nothing and has no route of its own that changes the
  disk: a move is the same removal to the holding area as Del, one
  journal entry through `POST /api/op`, refused in read-only and
  snapshot mode, and the duplicate copies are hashed again through
  `POST /api/hash` first. Its question, `GET /api/cleanup` (the folder,
  `under`, and how many of each list, `limit`, at most 1,000), reads
  the tree the service keeps, never the disk, behind the token, the
  Host check and the generation like the other whole-tree questions; a
  folder that is not there, a file, or a path that climbs out is
  refused as `ENOFOLDER`.
- The Shelf has no route of its own. What it keeps is a list of
  root-relative paths with each item's size and dates, in this
  browser's storage for this directory (`terrane.shelf.v1|<root>`), and
  every path read back is checked as a path from the root (no `..`, no
  leading `/`, nothing empty) before it is used. Gathering and Clear
  send nothing to the service. Move to…, Copy to… and Rename… are the
  `move`, `copy` and `renames` operations through `POST /api/op` that
  placing and the batch rename send, refused in read-only and snapshot
  mode, and journaled as one change each.
- The warm cache holds what a snapshot holds: names, sizes, dates and
  flags, never what a file contains. It is written only from a survey of
  the whole directory that ran to its end, and read back only when its
  meta names exactly this directory and its size agrees. `--read-only`
  still writes it, in the dataset home outside the directory, and
  `--no-warm` writes nothing. When the dataset home's real location is
  inside the directory (`TERRANE_DATA` set there, or a home folder or a
  whole drive given as the directory), no cache is kept, and the service
  says so when it starts.
- The address names a folder, never the token, and what follows `#` is
  not sent by the browser, so it never reaches the service.
- Looking inside an archive reads only its directory, through the same
  checks as a preview: the file's real location must be inside the root.
  It extracts and writes nothing, and an entry's name is never joined to
  a path on disk. The read stops at 100,000 entries, a 64 MB directory or
  4 seconds, and says what it left out.
- The tree the service keeps for a very large directory holds what the
  warm cache holds, and its routes only read. `GET /api/tree`,
  `GET /api/region` and the questions that walk the whole tree (`find`,
  `marks`, `survey`, `sessions`, `places`) take the token and the Host
  check like every route, are never stored by the browser, and answer
  in read-only and snapshot mode. Every path a request names passes the
  same lexical check as any other; reading a folder again lists it
  through the guard, inside the root, as a survey does, and snapshot
  mode reads nothing from disk. A name from the tree is never joined to
  a path on disk except through the guard. Each list a request carries
  has a cap (64 folders, 100 names, 50 folders read again, 1,500
  folders' marks, a page of 5,000 matches), and a request past one, or
  malformed, is refused with a code and a sentence.
- Checking the warm cache (`GET /api/check`) reads folder and file
  times only, inside the root and outside the holding area, through the
  guard; it opens no file and runs nothing, and snapshot mode refuses
  it.
- The service listens on `127.0.0.1` only, checks the Host header, and
  requires a per-session token on every API call. The cookie that lets
  thumbnails load carries a secret of its own, named for the port, which
  opens thumbnails and nothing else.
- The page, which carries the token, is never stored by the browser. The
  files it loads are kept and revalidated by a weak ETag, so one that has
  not changed costs a 304 instead of a download.

Limits worth knowing: the journal keeps the latest 500 changes;
`.terrane-trash` lives inside your directory, so on a OneDrive folder it
will sync until purged; hidden items are detected by dot prefix only, not
by the Windows hidden attribute; Survey again, after a warm start's
check failed, holds two copies of the tree while it runs; until the
sweep after a check reaches it, a file rewritten in place shows its old
size and date. In regions, after a change the service works out the
survey again and the page asks its search again; while either runs
(about 0.4 s and 0.2 s at 5,000,000 entries) region answers wait, and
they are paced to run at most about an eighth and a seventh of the
time.

There is no build step. Edit a file and reload the page. A feature lives
in its own module, listed in `web/js/features.js`, and reaches the
controller only through the registries it is handed; `docs/ARCHITECTURE.md`
section 7 describes them. The design decisions and their trade-offs are in
`docs/ARCHITECTURE.md`; the staged plan, the minimum filesystem scope and
the exploration loop are in `docs/ROADMAP.md`. The look the world's blocks
are built toward, Precision Architectural Terrain, is in
`docs/ART-DIRECTION.md`.

For GitHub Pages (deploy from the `main` branch, root folder), the root
`index.html` forwards visitors to `web/`, so the interface keeps a
single page. Pages has no service, so there the page runs the demo
world: `web/js/demo.js` answers every request to `/api/` in the page
from `web/js/demo-service.js`, over the tree `web/js/demo-world.js`
builds. Nothing a visitor does is sent anywhere. The demo answers the
region routes and the whole-tree questions too, through the same
`columns.js` the service uses, and `?regions` in the page's address
draws the demo world in regions.
